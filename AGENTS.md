# AGENTS.md

Frontend-only React 19 + Vite 8 + TypeScript SPA ("SSM"). No backend, no tests, no CI.

## Commands

- Dev server: `npm run dev` (or `RUN.bat`)
- Lint: `npm run lint` (oxlint — there is no ESLint)
- Typecheck/build: `npm run build` runs `tsc -b && vite build`. There is no separate typecheck script; use `npx tsc -b` to typecheck alone.
- Verify changes with `npm run lint`, then `npx tsc -b`. No test framework exists — do not invent test commands.

## Architecture

- Four router routes exist (`src/App.tsx`): shared `/login`, operator `/dashboard`, student `/student`, teacher `/teacher`. Guards are role-aware via the localStorage `role` key (`operator`/`student`/`teacher`): an unauthenticated user goes to `/login`, a logged-in user hitting another role's route is redirected toward their own home where one exists (StudentRoute sends operators to `/dashboard`, TeacherRoute sends operators/students home; stray teachers on `/dashboard` just get `/login`), and `/login` itself bounces already-authenticated users to `homeFor(role)`; the wildcard falls back by role (else `/login`). Within each side, the sections — operator: students, teachers, pay, absence, publications, user management; teacher: Courses, Exams & Notes, Class, Planning; student: Courses, My Payment, Announcements, Absence — are NOT routes; they swap via `useState` inside `src/components/Layout.tsx`, `src/pages/teacher-portal/TeacherLayout.tsx`, and `src/pages/student-portal/StudentLayout.tsx`. To add a section, update that layout's `menuItems` and `pages` maps. (`MyInfoPage.tsx` still exists in the student-portal folder but is not wired into any menu.)
- All persistence is browser localStorage: fake auth via `isLoggedIn`(string `"true"`)/`role` keys (read by route guards in `src/App.tsx`) plus `currentStudentId`/`currentTeacherId` for portal sessions; entity lists keyed by simple names (`students`, `teachers`, `payments`, `publications`, teacher-created `exams` + `grades`, teacher-created courses in `teacherCourses`, daily lesson logs in `teacherPlanning`, attendance as date maps in `studentAttendance`). Login data (`password`/`blocked`) lives directly on the records inside the `students` and `teachers` keys. Clearing site data resets everything.
- The portals share storage with no copies: student pages read the operator-managed keys directly (`MyPaymentsPage` reads `payments`; `AnnouncementsPage` reads `publications`; login reads `students`), and teacher pages likewise (`GradesPage`/`MyClassPage` filter `students` by the teacher's program+training). Changing an operator entity's shape breaks both portals too. Resolve sessions with `loadCurrentStudent()` (`src/pages/student-portal/currentStudent.ts`) or `loadCurrentTeacher()` (`src/pages/teacher-portal/currentTeacher.ts`); both end the session if the record disappears.
- Login is ONE page for all three roles: `/login` (`src/pages/LoginPage.tsx`), a single name+password form with no role picker. Submit checks, in order: (1) `admin`/`admin123` → operator; (2) `teachers` records — **exact case-sensitive** trimmed full-name match; credentials matching a teacher whose `blocked === true` show "Access has been blocked by the center." and stop; (3) `students` records — **case-insensitive** trimmed full-name match, same blocked rule; (4) anything else → one generic "Incorrect name or password." error. A blocked account whose password is WRONG gets the generic error (blocked check runs only after a credential match). Success sets `isLoggedIn`/`role` plus `isStudentLoggedIn`+`currentStudentId` or `isTeacherLoggedIn`+`currentTeacherId`; each layout's logout and its deleted-record effect navigate back to `/login`. The former `/student/login` and `/teacher/login` pages/routes are gone.
- Account lifecycle lives in `src/pages/users/userAccounts.ts`: kind-generic helpers (`AccountKind = "students" | "teachers"`, default `DEFAULT_ACCOUNT_PASSWORD = "std123"`). Boot seed `ensureDefaultPasswords()` in `src/main.tsx` fills a record's missing/empty password ONLY if it has no `accountInitialized` flag; every path that sets a password (seed, Create Account dialog, Reset Password, Add Student/Teacher form) stamps `accountInitialized: true`, and Delete Account strips credentials but KEEPS the flag — so deliberately deleted logins are never resurrected on reload, while pre-flag records still get seeded once. User Management page manages BOTH lists via Students|Teachers tabs over the shared `AccountsTable` component.
- `src/lib/trainings.ts` is the single source of truth for `PROGRAMS`, `TRAININGS`, and the static `COURSES` schedule data (keyed by program → training); students, teachers, pay, absence, and the student Courses page all import from it. Add a program/training/course only there. Note: `COURSES` covers only some trainings and its keys are looked up by exact training name (`COURSES[student.program]?.[student.training] ?? []`); several current `TRAININGS` entries have no matching key, so those students legitimately see "No courses scheduled yet". Course cards render via the shared `src/components/CourseCardsGrid.tsx` (per-training thumbnail from `src/assets/img/courses/<slug>.jpg`, gray placeholder when missing).
- Teacher courses extend the seeded schedule: `MyCoursesPage.tsx` has My Courses|Add Course tabs; Add Course auto-scopes to the teacher's program+training and persists `{id, teacherId, program, training, name, day, time, thumbnail?, published?, materials?}` under `teacherCourses` (`materials` entries hold `{name, type}` metadata only — no file data is stored). `published` is an auto-stamped creation timestamp (never asked from the user, preserved on edit) rendered by `CourseCardsGrid` as "Added <date>"; Day options are Monday–Friday and Time is a fixed slot list, both dropdowns. Optional thumbnail uploads are downscaled client-side to a ≤400px-wide JPEG data URL before storage — `saveTeacherCourse()` returns false on localStorage quota failure, shown as an inline form error. The Add Course form also has a Course Materials section (video/PDF/Word multi-upload) whose working list is removable pre-submit and replaces the stored `materials` wholesale on save. CRUD helpers live in `trainings.ts`. Read schedules through `loadScheduledCourses(program, training)` — the merged view where seeded entries carry no `id`/`teacherId`; both portals use it, so teacher-added courses (custom thumbnails included) appear immediately for matching students. My Courses renders through the shared `CourseCardsGrid` with its `renderActions` overlay: Edit/Delete show only on rows whose `teacherId` matches the session teacher; the grid's materials count chip + names dialog is gated behind its `showMaterials` prop (only My Courses passes true). Edits preserve the original scoping, deletes confirm via AlertDialog (no cascade).
- Teacher exams/grades: `ExamsPage` stores into the `exams` key (`{id, teacherId, program, training, title, date, notes?, course?, attachment?}`), auto-scoped to the teacher's own program+training at creation; the inline Add Exam form (tab 1 of `ExamsNotesPage.tsx`) picks the course by NAME from `loadScheduledCourses(...)` because seeded courses carry no id, and its file input stores only the chosen file's name — no real upload. Deleting an exam cascades its grades with a confirm dialog that names the grade count. `GradesPage` upserts `{id: "<examId>:<studentId>", examId, studentId, score}` records into `grades` in one bulk write; blank inputs clear a grade. Both read the class roster by filtering `students` on the teacher's program+training. In the sidebar they appear as one "Exams & Notes" section with internal Add Exam|Grades tabs.
- Teacher planning log: `PlanningPage.tsx` (sidebar "Planning") stores `{id, teacherId, date, course?, content}` records under `teacherPlanning` (`src/pages/teacher-portal/planning.ts`), filtered strictly by `teacherId`; the course dropdown reads names from `loadScheduledCourses(...)` like exams. UI is a hand-rolled Monday–Sunday week view with NO date library (state is a `Date` anchored on `startOfWeek(today)`, stepped ±7 days); day cells mark entries and clicking one opens an add/edit/delete dialog. Export as Excel (SheetJS `aoa_to_sheet` + `writeFile`) / PDF (`jspdf` + `jspdf-autotable`) emit only the viewed week's entries and are disabled when it has none.
- Bulk import parses uploaded `.xlsx`/`.csv` client-side with SheetJS (`importStudents.ts` / `importTeachers.ts`).
- Feature folders live in `src/pages/<feature>/` as `<Feature>Page.tsx` plus list/form subcomponents.

## Non-code folders

- `init/` holds the product specs (`PRD.md`, `plan.md`, `bugs.md`) and `claude/` holds the original build prompts — reference material, not app code. `README.md` is stock Vite template boilerplate. Root `accessloginpage.md` documents portal logins; note only `admin`/`admin123` works out of the box — teacher/student logins exist only after records are created from the operator side. `superbase/` is a stray non-app folder (the name suggests Supabase; there is NO backend integration — ignore it).

## Stack quirks

- Tailwind v4 via `@tailwindcss/vite`: there is intentionally no tailwind.config.js. Theme tokens and colors are defined in `src/index.css` (`@theme inline` block); edit CSS there instead of creating a config file.
- shadcn/ui uses the Base UI flavor (`style: base-nova` in components.json): components in `src/components/ui/` wrap `@base-ui/react`, not Radix. Add new primitives with `npx shadcn add <component>`; icons come from lucide-react.
- Path alias `@/*` → `src/*` (must stay in sync in both `vite.config.ts` and `tsconfig.app.json`).
- TS settings shape code style: `verbatimModuleSyntax` (types need `import type`), `erasableSyntaxOnly` (no enums, namespaces, or parameter properties), plus `noUnusedLocals`/`noUnusedParameters`.
