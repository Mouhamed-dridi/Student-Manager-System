# AGENTS.md

Frontend-only React 19 + Vite 8 + TypeScript SPA ("SSM") backed by Supabase. No tests, no CI.

## Commands

- Dev server: `npm run dev` (or `RUN.bat`)
- Lint: `npm run lint` (oxlint — there is no ESLint; config in `.oxlintrc.json`)
- Typecheck/build: `npm run build` runs `tsc -b && vite build`. There is no separate typecheck script; use `npx tsc -b` to typecheck alone.
- Verify changes with `npm run lint`, then `npx tsc -b`. No test framework exists — do not invent test commands.
- Gotchas: `.\check.ps1` verifies live Supabase connectivity/table existence/anon read (prints table row counts); run it when Supabase pages fail. Note it hard-fails (exit 1) unless `.env.local` defines `VITE_SUPABASE_PUBLISHABLE_KEY` — it does NOT fall back to the anon key, even though the app accepts either. `cleardata.ps1` clears localStorage via CDP — the app stores session in cookies, so it does not clear logins and is effectively stale.
- Custom OpenCode command `verify-fix` (`.opencode/command/verify-fix.md`): before editing code that touches Supabase, verify the actual live table columns (schema.sql can drift); ask the user if unsure rather than guessing.

## Backend & environment

- Supabase is REQUIRED: copy `.env.example` to `.env.local` in the project root with `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` (or `VITE_SUPABASE_PUBLISHABLE_KEY`). `src/lib/supabase.ts` throws at import time when missing, so every page fails until configured; restart Vite after editing env files.
- Schema lives in `supabase/schema.sql` (idempotent; paste into the Supabase SQL Editor). Tables: `programs`, `trainings`, `students`, `teachers`, `payments`, `attendance`, `courses`, `exams`, `grades`, `publications`, `planning`, `settings`. RLS grants full anon access — there are NO Supabase Auth accounts; auth is the cookie session scheme below.
- ALL Supabase I/O goes through `src/lib/api.ts`: rows are snake_case, mappers convert to/from the camelCase shapes the UI uses. Add new tables/columns/mutations there, not inline in components.
- Realtime: pages that must live-update subscribe via `subscribeToTable(table, onChange)` from api.ts and refetch on any event (students' `CoursesPage`/`StudentDashboardPage` → `courses`, StudentsPage/UserManagementPage → `students`, TeachersPage/UserManagementPage → `teachers`, MyClassPage → `students` + `courses`, MyCoursesPage → `courses`). It only delivers events for tables added to the `supabase_realtime` publication — new tables need an entry in the idempotent Realtime block at the bottom of `supabase/schema.sql`. Those same pages also call `useRefetchOnFocus(refetch)` (`src/hooks/useRefetchOnFocus.ts`): a quiet fallback that refetches once when the tab/window regains focus after ≥5s in the background, covering the case where the realtime socket silently dropped while hidden — NOT the primary sync mechanism. (Realtime: pages in ALL portals subscribe — students' `CoursesPage` and `StudentDashboardPage` → `courses`, teachers' `MyCoursesPage` → `courses`, `MyClassPage`/`StudentsPage`/`UserManagementPage` → `students`+`courses`, `TeachersPage`/`UserManagementPage` → `teachers`.)
- Session state lives in cookies via `src/lib/session.ts`: `role` (`operator`|`student`|`teacher`), `currentStudentId`, `currentTeacherId`. No localStorage is used for session state; it is used ONLY for the settings fallback cache (see Settings below). Route guards in `src/App.tsx` read the role; session helpers `loadCurrentStudent()`/`loadCurrentTeacher()` read the person ID.

## Architecture

- Four router routes (`src/App.tsx`): shared `/login`, operator `/dashboard`, student `/student`, teacher `/teacher`. `/dashboard` mounts `src/pages/DashboardPage.tsx`, a thin wrapper that just renders `<Layout />` — NOT the stats page at `src/pages/dashboard/DashboardPage.tsx` (rendered by the sidebar's Dashboard section). Guards are role-aware: unauthenticated → `/login`; a logged-in user on another role's route bounces toward their own home where one exists (stray teachers on `/dashboard` just get `/login`); `/login` redirects authenticated users to `homeFor(role)`; the wildcard falls back by role. Sections within each side are NOT routes — they swap via `useState` inside `src/components/Layout.tsx` (operator: Dashboard, Students, Teachers, Pay, Absence, Publications, User Management, Trash, Settings; Pay is a nested submenu of Payments | History | Trash with `children` in its `menuItems` entry), `src/pages/teacher-portal/TeacherLayout.tsx` (Courses, Exams & Notes, Class, Planning), and `src/pages/student-portal/StudentLayout.tsx` (Dashboard, Courses, My Payment, Announcements, Absence, Settings — Dashboard is the default landing). To add a section, update that layout's `menuItems` and `pages` maps. The student portal header shows the active section title on the left and the avatar with the student's full name + program·training on the right. (`MyInfoPage.tsx` exists in student-portal but is wired into no menu.)
- Pages are async over Supabase. Session helpers `loadCurrentStudent()` / `loadCurrentTeacher()` (in `currentStudent.ts` / `currentTeacher.ts`) read the ID from cookies via `session.ts` and fetch the record from Supabase — returning null ends the session via each layout's deleted-record effect. Loading/error UI comes from `src/components/DataState.tsx` (`DataLoading`/`DataError`).
- Login is ONE page for all roles (`src/pages/LoginPage.tsx`), single name+password form, checks in order: (1) `admin`/`admin123` → operator; (2) teachers by **exact case-sensitive** trimmed full-name match; (3) students by **case-insensitive** trimmed full-name match. A matched account with `blocked === true` shows "Access has been blocked by the center." and stops; a WRONG password always gets the generic "Incorrect name or password." (blocked check runs only after a credential match). Success sets cookies via `session.ts`.
- Payment module audit/tracking (`src/pages/pay/`): rows are soft-deleted via `is_deleted = true` (with `deleted_at` = when) — `listPayments()` filters `.or("is_deleted.is.false,is_deleted.is.null")`, `listDeletedPayments()` the rest. The Trash page lists deleted rows and restores them (sets `is_deleted = false`, `deleted_at = null`). Public-store receipt tickets: the Payments list's printer icon opens `PaymentReceiptModal.tsx`, a compact 80mm-friendly receipt (center name from `getSystemName()`, student Program·Training resolved from the `students` record at open time, amount in USD like the dashboard, reference ID, date/recorded/issued timestamps); it prints only the `#receipt-print-area` via the `receipt-printing` body class + `@media print` rules in `src/index.css` (hidden everything else, black-on-white, dashed separators). Every edit goes through `updatePayment()` in api.ts, which diff-picks changed fields and APPENDS one `{changedAt, changedBy, changes:[{field, from, to}]}` entry to the payment's `edit_history` (jsonb array) column; the History page reads that column via `listPaymentHistory()` (joins `students` for names, newest first). `changed_by` = current cookie role, always "operator" — the Pay module is operator-only. `softDeletePayment`/`restorePayment` only flip the flag and never touch history. Student My Payments also reads `listPayments()`, so trashed rows disappear there automatically. The trash/history columns are probed ONCE at runtime (`detectPaymentsCapabilities` in api.ts): if `is_deleted`/`deleted_at`/`edit_history` are missing, no query ever references them (PostgREST rejects unknown columns) — `listPayments()` returns all rows, trash logs to an in-memory map, edits append to an in-memory log, and the Trash/History sub-pages show a tailored "not available" notice instead of erroring.
- General Trash (`src/pages/trash/GeneralTrashPage.tsx`): students, teachers, publications and attendance/absences share one Trash page (Payments keeps its own). Deleting from the Students/Teachers/Publications pages and the Absence page's attendance log soft-deletes (`is_deleted = true`, `deleted_at = NOW()`) when those columns exist (attendance soft-delete is `softDeleteAttendance([ids])`); `listStudents`/`listTeachers`/`listPublications` and the `listStudentAccounts`/`listTeacherAccounts` always exclude trashed rows, so trashed people cannot log in (login searches those lists) and a trashed person's session ends because `getStudentById`/`getTeacherById` return null for trashed rows. `loadAttendanceRecords`/`loadStudentAttendance` also exclude trashed rows. The Trash page renders `listGeneralTrash()` (newest first) with Restore/STUDENT-TEACHER badge (attendance rows reuse the person's type) and Details (program - training for absences) and Restore (`restoreStudents`/`restoreTeachers`/`restorePublication`/`restoreAttendance` — clears the flags) and permanent delete (`hardDeleteStudents`/`hardDeleteTeachers`/`hardDeletePublication`/`hardDeleteAttendance` — real `.delete()`) confirm dialogs. `generalTrashCapabilities()` probes `is_deleted`/`deleted_at` per table at runtime — when a table lacks them, its deletes/restores fall back to a session-only in-memory map and the page shows a tailored notice instead of erroring.
- Dashboard (`src/pages/dashboard/DashboardPage.tsx`): the operator's default page; `getDashboardStats()` in api.ts aggregates active counts, a 30-day attendance-rate proxy (presence records ÷ 30 days × active people, capped at 100%), paid/pending revenue KPIs, and the last-6-month, by-plan and by-program series rendered with recharts.
- Settings (`src/pages/settings/SettingsPage.tsx`): operator page with General | Preferences | System | About tabs reading/writing the `settings` key/value table via `getSettings`/`saveSettings` (SQL null = cleared preference). Keys today: `system_name`, `university_name`, `logo_url` (downscaled PNG data URL from the Logo Upload control), `language`, `dark_mode` (boolean). When the `settings` table is missing, reads fall back to a localStorage cache (`ssm-settings`) instead of erroring; `saveSettings` always mirrors the rows to that cache first, then best-effort upserts the DB. `dark_mode` toggles the app-wide `.dark` class via `applyDarkMode()` — applied at bootstrap in `main.tsx` (synchronous `getCachedSettings()`, then an async DB refresh), so it works before login and even without the table. `system_name` drives the operator sidebar/top-bar branding through `getSystemName()` (falls back to "SSM" while the table doesn't exist). language is a stored-only preference — no UI is translated. Notification toggles and the Admin Profile card/keys no longer exist. The System tab also hosts "Sync Data": `reconcileAttendanceProfiles()` in api.ts scans active `attendance` rows for NULL `program`/`training` (or the generic `"General"` `class_name`), cross-references each by type + case-insensitive `full_name` against `students`/`teachers` (via `listStudents`/`listTeachers`, trashed people excluded), and backfills only gaps — stored values are never overwritten — returning an `AttendanceSyncSummary` (scanned/needingFix/matched/updated/unmatched/failed + per-row `details`) rendered as a result panel. The same logic exists as an idempotent SQL function `public.reconcile_attendance_profiles()` (security definer, returns scanned/needing_fix/updated/unmatched) at the bottom of the attendance block in `supabase/schema.sql`, so it can be run from the SQL Editor or scheduled. Note: `students` stores only `program_id`/`training_id` FKs — the JS path resolves the `programs(code)`/`trainings(name)` strings via joins — while `teachers` carry free-text `program`/`training` columns added by schema.sql. The SQL function needs schema.sql applied (it references those columns).
- Portals share storage with no copies: student pages query the same tables the operator writes (`MyPaymentsPage` ← `payments`; student names are resolved at read time by joining `students` on `student_id` — the table keeps only snapshot-free columns (`id, student_id, amount, plan_type, payment_date, status, created_at, is_deleted, deleted_at, edit_history`), so renaming/removing snapshot columns breaks inserts; `AnnouncementsPage` ← `publications`). Teachers carry an OPTIONAL `program`/`training` (free-selectable on their profile, plus a free-text `specialty`) — used to enrich their attendance rows; teacher Exams/Grades/Class pages are still scoped by `teacher_id` ownership: exams belong to the creator; the Class/Grades roster comes from students matching the program/training of the courses the teacher teaches (`classRosterForTeacher` in api.ts joins `courses` by `teacher_id` then matches `students`). Changing an entity's shape breaks both sides.
- Account logins are just `password`/`blocked` columns on the people tables (null password = no account). `src/pages/users/userAccounts.ts` holds per-kind defaults — `DEFAULT_TEACHER_PASSWORD = "tch123"`, `DEFAULT_STUDENT_PASSWORD = "std123"` — plus `defaultAccountPassword(kind)` and `hasAccount()`; Add/Edit Student/Teacher forms, Create Account, and Reset Password all default to their kind's value. User Management manages both lists via Students|Teachers tabs over the shared `AccountsTable`.
- Programs/trainings have TWO sources, and they are easy to confuse. The DB `programs`/`trainings` tables (schema.sql) drive every form dropdown — Student/Teacher forms, Add Absence — via `listPrograms()`/`listTrainings()` (the teacher Add Course form deliberately has none), and every student insert resolves the displayed code/name strings back to FK ids through `resolveProgramTrainingIds()` in api.ts, so an EMPTY `programs`/`trainings` table silently drops program/training on new students. The static `PROGRAMS`/`TRAININGS` strings in `src/lib/trainings.ts` are a separate list that only powers the student portal's seeded course schedule.
- `src/lib/trainings.ts` owns `PROGRAMS`, `TRAININGS`, the static seeded `COURSES` schedule (keyed program → training), and `loadScheduledCourses(program, training)` — the ASYNC merged view (seeded entries carry no `id`/`teacherId`; rows from the `courses` table do) used by the student portal only (teachers have no assignment, so their courses come straight from the `courses` table). When the student's `program_id`/`training_id` FKs both exist, it fetches `listTeacherCourses({ programId, trainingId })` server-side; otherwise ALL course rows are fetched and a `courseInClass` name match (trimmed + case-insensitive `programs(code)`/`trainings(name)` strings, with FK-id equality preferred) keeps the in-class ones. Most current `TRAININGS` entries have NO matching `COURSES` key, so those classes legitimately show only teacher-added courses. Add static schedule entries only here; the DB `programs`/`trainings` rows are a separate source (see the bullet above). Cards render through shared `CourseCardsGrid`: a course's own Storage `thumbnail` URL wins, else a static `src/assets/img/courses/<slug>.jpg` keyed by training-slug (accents/apostrophes stripped to `-`), else a gray placeholder.
- Teacher courses (`MyCoursesPage.tsx`, My Courses|Add Course tabs): `listTeacherCourses({ teacherId?, programId?, trainingId? })` filters `courses` server-side for any supplied option — the My Courses tab, Exams course dropdown, Planning course options, `classRosterForTeacher` and the `teacherCourseAssignment` fallback pass `{ teacherId }`, so a teacher never receives another teacher's rows; the student portal's `loadScheduledCourses` passes `{ programId, trainingId }` to get only the student's class. Call it with `{}` only where ALL courses are needed. The Add Course form has NO program/training selectors — program/training come from `teacherCourseAssignment()` in api.ts (profile `teachers.program`/`training` first, else the class of the teacher's existing courses, else legacy record text; re-fetched at save time inside `courseTargetIds`), so a course can never be written outside the teacher's own assignment. `saveTeacherCourse()` THROWS on failure (callers catch it and show inline); `deleteTeacherCourse()` returns a boolean. Optional thumbnails are downscaled client-side to a ≤400px-wide JPEG blob, then uploaded to the `cours` **Supabase Storage** bucket via `uploadCourseThumbnail()` — the DB stores only the `thumbnail_url`. The bucket + anon read/insert policies come from the idempotent Storage block at the top of the courses section in `supabase/schema.sql`; if it's missing, uploads fail with a readable "bucket does not exist" error. `published` is an auto creation timestamp (`published_at`, never asked, preserved on edit) rendered as "Added <date>". `description` is an optional free-text textarea stored on the course row and shown on the cards below the title. `materials` hold `{name, type}` metadata only — no file data anywhere. The `courses` table still has `day`/`time_slot` columns but the form no longer writes them, so teacher-added cards show no day/time (only seeded schedule entries have them). Delete confirms via AlertDialog, no cascade. My Courses passes `showMaterials` + `renderActions` into `CourseCardsGrid`.
- Exams & notes: `ExamsPage` writes `exams` scoped at creation with the exam's `teacher_id` and snapshot `program`/`training` pulled from the course chosen in the form; the Course dropdown lists the teacher's OWN courses by name (seeded schedule courses are absent for teachers). Its file input stores only the chosen file's name. Deleting an exam cascades its grades after a confirm dialog naming the count (`countGradesForExam` + `deleteExamCascade`). `GradesPage` saves one exam's scores wholesale via `saveGradesForExam` (deletes all of that exam's grades, reinserts non-blank inputs), so leaving an input blank clears that student's grade; its roster is `classRosterForTeacher`. Sidebar shows one "Exams & Notes" section with internal Add Exam|Grades tabs (`ExamsNotesPage.tsx`).
- Planning log (`PlanningPage.tsx`): rows in `planning` filtered strictly by `teacherId`; hand-rolled Monday–Sunday week view with NO date library (a `Date` anchored on `startOfWeek(today)`, stepped ±7 days); day cells open an add/edit/delete dialog; Excel (SheetJS `aoa_to_sheet` + `writeFile`) / PDF (`jspdf` + `jspdf-autotable`) export only the viewed week and are disabled when it has none.
- Attendance is a single unified log in the `attendance` table (`AttendanceLog.tsx`): one denormalised row per record with `id, type ('student'|'teacher'), full_name, class_name, date, time, created_at` plus optional `program`/`training` snapshots and soft-delete `is_deleted`/`deleted_at` — no `student_id`/`teacher_id`/`present`, and no names are joined (class_name carries the program·training for students or the specialty for teachers). Writes go through `insertAttendanceRecords`/`updateAttendanceRecord`, which ALWAYS resolve program/training in the payload: explicit form/file values win, and any row still missing them is backfilled from the person's `students`/`teachers` record by lowercase full-name lookup (`attendanceToWriteRows`), so the columns are never left NULL when the profile has them; `class_name` falls back to training → program → specialty → "General" (NOT NULL in live deployments). The operator Absence page renders one table with Type / Full Name / Class·Program·Specialty / Date / Time columns, no tabs and no Save button; `loadAttendanceRecords()` fetches ALL rows from Supabase (excluding soft-deleted ones) and the search input filters the rendered rows client-side by `fullName`/`className` (case-insensitive), so no rows are ever mocked. The student portal reads its own history via `loadStudentAttendance(fullName)` (type=student + full_name match; session stores the id, so it loads the student record first).
- Bulk import parses uploaded `.xlsx`/`.csv` client-side with SheetJS (`src/pages/students/importStudents.ts` / `src/pages/teachers/importTeachers.ts`), then bulk-inserts through api.ts.
- Feature folders live in `src/pages/<feature>/` as `<Feature>Page.tsx` plus list/form subcomponents.

## Non-code folders

- `supabase/schema.sql` is the executable source of truth for the DB (see Backend section). `init/` holds product specs (`PRD.md`, `plan.md`, `bugs.md`, `inti.md`) — reference material, not app code. Same for root `*.md` spec/prompt docs (`backend.md`, `TDD*.md`, `PRD*.md`, `vibe-code-prompts-*.md`) and the `claude/` and `md/` doc folders. `README.md` is stock Vite boilerplate. Root `accessloginpage.md` documents portal logins: only `admin`/`admin123` works out of the box — teacher/student logins exist only after records are created from the operator side (password defaults to `tch123`/`std123` respectively). `superbase/` (extra "e") is a stray non-app folder with a DB password file — ignore it entirely.

## Stack quirks

- Tailwind v4 via `@tailwindcss/vite`: intentionally NO tailwind.config.js. Theme tokens and colors live in the `@theme inline` block of `src/index.css`; edit CSS there instead of creating a config file.
- shadcn/ui uses the Base UI flavor (`style: base-nova` in `components.json`): components in `src/components/ui/` wrap `@base-ui/react`, not Radix. Add primitives with `npx shadcn add <component>`; icons come from lucide-react.
- Path alias `@/*` → `src/*` must stay in sync in both `vite.config.ts` and `tsconfig.app.json` (also declared in root `tsconfig.json`).
- TS settings shape code style: `verbatimModuleSyntax` (types need `import type`), `erasableSyntaxOnly` (no enums, namespaces, or parameter properties), plus `noUnusedLocals`/`noUnusedParameters`.
